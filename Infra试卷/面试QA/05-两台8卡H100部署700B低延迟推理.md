# 05. 两台 8 卡 H100 部署 700B 低延迟推理

## 1. 问题

使用两台 8 卡 H100 部署 700B 级模型，精度 FP8，要求：

```text
GPU       = 2 nodes × 8 H100
Precision = FP8
TTFT      < 2s
TPOT      < 50ms
限制      = 不靠调 max-num-seqs / max-num-batched-tokens 解决
```

需要明确：

- 700B 是 dense 700B，还是 DeepSeek-V3/R1 这类 671B MoE；
- H100 是 SXM 还是 PCIe，节点内是否有 NVSwitch；
- 节点间是否有 IB/RoCE + GPUDirect RDMA；
- TTFT/TPOT 统计是否包含排队、tokenization、网络和 sampling；
- prompt 长度、输出长度、并发和 P95/P99 口径。

## 2. 方案

### 2.1 先判断模型类型

FP8 权重大致为：

```text
700B params × 1 byte ≈ 700 GB
```

16 张 80GB H100 原始显存为：

```text
16 × 80GB = 1280 GB
```

推理不需要保存梯度、优化器状态和反向激活。常驻主体是 weight，但仍要预留：

- FP8 scale / metadata；
- KV cache；
- workspace、CUDA graph、通信 buffer；
- tokenizer/logits/sampling 相关 buffer；
- 框架运行时碎片。

如果是 dense 700B：

```text
dense decode FLOPs / token ≈ 2 × 700B = 1.4e12
```

`TPOT < 50ms` 已经接近理想硬件下限，真实系统还要付出 attention、KV、通信和调度开销，
不能直接承诺。

如果是 DeepSeek-V3/R1 风格 MoE：

```text
total parameters     ≈ 671B
activated parameters ≈ 37B / token
```

这个目标才有工程讨论空间。主答案应按 MoE 部署设计。

### 2.2 MoE 主方案

```text
EP = 16
TP = 1 or 2
DP = 16 / TP
```

- Expert 层：按 EP=16 分散到 16 张 GPU。
- Attention / dense 层：尽量用 DP attention 或小 TP，避免大 TP 跨节点。
- Decode：使用 low-latency MoE all-to-all。
- Prefill：使用 high-throughput MoE all-to-all。
- KV cache：优先 FP8 KV cache。
- Attention：使用 MLA / paged attention 优化路径。
- GEMM：使用 FP8 Tensor Core kernel，如 DeepGEMM、FlashInfer、TensorRT-LLM backend。

为什么不优先 `TP=16`：

- Decode 每个 token 都会触发跨节点 collective；
- 小消息阶段容易 latency-bound；
- TP 越大，单卡 GEMM 越碎；
- MoE 的主要参数在 experts，EP 比 TP 更贴合模型结构。

### 2.3 Dense 700B 备选

如果模型明确是 dense 700B，只能给高风险方案。

方案 A：

```text
TP = 8
PP = 2
```

- 每个节点一个 PP stage；
- TP collective 留在节点内；
- 跨节点只传 stage activation；
- 代价是 decode 要串过两个 stage，低并发下 PP bubble 明显。

方案 B：

```text
TP = 16
PP = 1
```

- 单 token 计算被 16 卡分摊；
- 代价是每层 collective 跨节点；
- 对 IB/RoCE、NCCL、GDRDMA 和拓扑极其敏感。

结论：

```text
dense 700B + 16 H100 + TPOT < 50ms
```

不应作为可稳定交付的默认承诺。更现实的办法是加卡、换 H200/B200、降低精度到
W4A8/FP4，或换成 active 参数更小的 MoE。

### 2.4 P/D 分离

Prefill 和 Decode 的瓶颈不同：

```text
Prefill:
  长 prompt、矩阵计算、KV 写入

Decode:
  小 batch、小消息通信、KV 读取、调度延迟
```

P/D 分离可以：

- 单独优化 TTFT 和 TPOT；
- 避免 prefill 插入 decode 拉高 tail TPOT；
- prefill 用 high-throughput backend；
- decode 用 low-latency backend；
- 通过 NIXL / UCX / GDRCopy / LMCache 传 KV。

限制：

- 如果 16 张 H100 只够放一份模型，就不能拆成两套完整实例；
- 这种情况下只能做逻辑分阶段调度、chunked prefill、prefix cache，或增加机器。

### 2.5 Prefix Cache 和 KV 复用

TTFT 主要受 prefill 影响。对固定系统 prompt、工具 schema、RAG 模板、多轮对话，应使用：

- prefix cache；
- prompt token ids 复用；
- FP8 KV cache；
- KV transfer 避免重复 prefill。

边界：

- 只对重复前缀有效；
- 冷 prompt 仍然要完整 prefill；
- cache miss rate 是核心指标。

### 2.6 MTP / 投机解码

如果模型支持 MTP，或有质量足够的 draft model，可以降低用户感知 TPOT。

```text
普通 decode:
  一次 step 接受 1 token

MTP / speculative:
  一次 step 接受多个 token
```

前提：

- accept rate 足够高；
- draft/MTP 额外计算小于节省的主模型 step；
- TPOT 按 accepted token 统计。

### 2.7 网络和系统检查

必须确认：

- 两台机器是 8 卡 H100 SXM + NVSwitch；
- 节点间是 IB/RoCE，而不是普通 TCP；
- NCCL 日志中跨节点走 `NET/IB/GDRDMA`；
- 容器具备 RDMA、IPC_LOCK、host network 或等价权限；
- NIC、GPU、NUMA、rail 绑定正确；
- decode 小包路径使用 DeepEP low-latency 或等价实现；
- sampling、tokenizer、logits processor 没有成为 CPU 瓶颈。

如果跨节点通信退回 Socket，`TPOT < 50ms` 基本不可达。

### 2.8 验证

- 分别记录 queue time、tokenization、prefill、decode、sampling、detokenization。
- 分别看 TTFT、TPOT/ITL、E2E latency 的 P50/P95/P99。
- 使用真实 prompt 长度分布，不只测短 synthetic prompt。
- 用 Nsight Systems 检查 prefill、decode、A2A、collective、KV 读写时间。
- 用 NCCL / RDMA 日志确认跨节点路径。
- 对 MoE 记录每层每 expert token 数、hot expert、A2A 时间和 load balance。

## 3. 面试追问

### Q1：为什么不能只调 max-num-seqs？

A：

- `max-num-seqs` 改的是 admission 和 batching 形态。
- 它不能减少 700B 的 per-token 计算、KV 读写和跨节点通信。
- 题目禁止调它，本质是在问模型结构、并行、通信和 kernel 路径。

### Q2：为什么 MoE 比 dense 更可能达标？

A：

- Dense 每个 token 激活全部 700B 参数。
- MoE 总参数大，但每个 token 只激活部分 experts。
- DeepSeek-V3/R1 这类模型约 671B total、37B activated。
- 低延迟优化重点从全量 GEMM 变成 active expert GEMM 和 token dispatch。

### Q3：为什么不优先 TP=16？

A：

- TP=16 会让每层 collective 跨节点。
- Decode 是小消息延迟敏感场景，固定延迟占比高。
- H100 节点内 NVSwitch 快，节点间 IB/RoCE 慢一个层级。
- 除非实测证明更快，否则优先用 EP 和小 TP。

### Q4：P/D 分离一定能做吗？

A：

- 不一定。
- P/D 分离通常需要 prefill 和 decode 各放一份模型。
- 如果 16 张 H100 才够放下一份模型，就需要增加机器或接受非严格 P/D。

### Q5：TTFT<2s 主要靠什么？

A：

- 短 prompt：prefill kernel、CUDA graph、FP8、MLA attention。
- 长 prompt：prefix cache、chunked prefill、P/D 分离、KV 复用。
- 如果 prompt 很长且 cache miss，`TTFT < 2s` 不能直接承诺。

### Q6：TPOT<50ms 主要靠什么？

A：

- MoE EP 而不是 dense 全量计算；
- decode low-latency A2A；
- FP8 GEMM 和 FP8 KV；
- CUDA graph 覆盖 decode；
- 避免跨节点大 TP collective；
- 必要时使用 MTP / speculative decoding。
